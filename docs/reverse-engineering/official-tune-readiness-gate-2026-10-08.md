# Official Linux trace: why the T27 tune and lock checks did not test RF

## Finding

The bounded official-library trace does not show a successful tune to 557142 kHz. `TF_DTV_SetTunerFreq(..., lane=1, 557142, 6)` returns 1, but the initialized-and-streaming branch in `DTV_SetTunerFreq` waits 400 ms and returns 1 without calling `TunerReset` or `Tnim_AcquireFrequency`. Consequently no T27 PLL writes are expected from that call. The only PLL values in the trace are the initialization tune to 773143 kHz. The reported `TF_DTV_TunerLockCheck` result 0 is also not an RF measurement in this state: `DTV_TunerLockCheck` returns 0 before calling `Tnim_IsLocked` whenever the internal stream/seed flag is nonzero.

This explains the apparent contradiction between API success and absent T27 tuner writes. The current trace cannot establish whether the RF path locks at 557142 kHz.

## Evidence

- `Transform.o`, `.text+0x1b0..0x1e3`: `TF_DTV_SetTunerFreq` selects the control object by lane and forwards the 64-bit `ULONG` frequency and byte bandwidth. `Transform.h` declares `(PVOID, BYTE, ULONG, BYTE)`; `Data_define.h` defines `ULONG` as `unsigned long` on this x86-64 build. The observed 557142 / BW 6 call therefore has the expected ABI and units.
- `DTV_Lib.o`, `DTV_SetTunerFreq` `.text+0x6700..0x6768`: when `ctrl+0x1d40` is nonzero, the function checks byte `ctrl+0x30d60`. If it is 1, it delays `0x190` ms and returns 1 immediately. The `TunerReset` and `Tnim_AcquireFrequency` calls are on the later path (`0x6790` onward), which this condition bypasses.
- `Transform.o`, `TF_DTV_Init` `.text+0x3bf..0x3d6`: after `DTV_StreamThreadRun` succeeds, the wrapper stores 1 at `ctrl+0x30d60`.
- `DTV_Lib.o`, `DTV_TunerLockCheck` `.text+0x5000..0x5034`: with initialized count nonzero, it returns 0 immediately when `ctrl+0x30d60` is nonzero. Only the zero case calls `Tnim_IsLocked`.
- `TunerControl.o`, `TC_IsLocked` `.text+0x880`: the terrestrial lock check reads demod register `0xb0` at I2C slave `0x30`, mode 1, and tests its low nibble for `9`. This is the RF-oriented check hidden behind the `DTV_TunerLockCheck` gate. The guest trace's lock API calls therefore cannot be treated as those register reads.
- `DTV_Lib.o`, `DTV_GenEncSeed` `.text+0x8e0e`: a successful seed-generation path stores zero to `ctrl+0x30d60`. The inspected `TF_DTV_GenEncSeed` is a separate API; it is not part of ordinary init/start/read. Reaching this store is tied to the seed-generation flow. This finding does not authorize invoking it with guessed or fabricated inputs.
- Parent's trace comparison: init emitted the 773143 kHz PLL sequence (`01=04, 02=15, 03=e7, 04=9f, 05=0f, 06=8a`). No subsequent sequence matching the known 557142 kHz T27 values (`01=02, 02=17, 03=db, 04=6f, 05=0f, 06=88`) appears after the tune call. The lock API returned 0 during the same run.

## `bMode` and other candidate causes

`TF_DTV_Init(extension, lane, bMode, mode)` maps `bMode==1` to internal `DTV_Init` selector 2, while `bMode==0` maps to selector 0 (`Transform.o`, `.text+0x330..0x366`). The lane separately selects the control object. Selector 2 takes a different filter setup branch from selector 0; this is not evidence that lane 1 should use `bMode=0`, nor does it explain the skipped tune branch, which checks `ctrl+0x30d60`.

The frequency/bandwidth ABI is consistent, and the tune routine's early return precedes PLL acquisition and its later tuner gain writes. Thus the trace provides no evidence that a missing post-tune gain write caused this particular no-lock result. The startup GPIO guard also makes this run a deliberately modified reference initialization; it remains a separate limitation, not a source-proven explanation for the absent T27 PLL sequence.

## Bounded conclusion / next safe evidence

Do not use the return value 1 from `TF_DTV_SetTunerFreq` as proof of retuning, or the return value 0 from `TF_DTV_TunerLockCheck` as proof of RF unlock, in the post-`Init` state shown here. Do not alter the cached flag directly or call seed generation with unknown input.

The source reviewed so far exposes no ordinary public RF-only API that both clears this gate and safely retunes the initialized streaming object. `TF_DTV_UnInit` is a public lifecycle operation, but it stops the stream and deinitializes/powers down the tuner; the reviewed source does not establish that calling tune after uninitialization is a supported sequence. Therefore this is not a recommendation to do that. A useful non-invasive check is to distinguish wrapper-gated lock calls from the already-observed raw demod `0xb0` reads; any new tuning experiment needs a source-supported lifecycle that reaches `Tnim_AcquireFrequency` without bypassing seed/state validation.

## Optional lower-level RF diagnostic prepared for parent review

The parent requested a bounded diagnostic that separates the public wrapper gate from the tuner primitive. The existing standalone harness at `/config/.tools/asicen-work/official-trace-harness.cpp` now has an opt-in `--rf-diagnostic` mode; the normal mode is unchanged. This mode logs the normal API lock result as `public_api_lock_*`, then resolves local1's control pointer read-only from extension offset `0x460` (the `Transform.o` wrappers use `extension+0x458+lane*8`). Before calling the vendor primitive it validates the control object's extension back-reference at `+0x1d38`, local index at `+0x1d30`, init count at `+0x1d40`, expected stream gate at `+0x30d60`, and three tune scratch words. For local1, `DTV_SetTunerFreq` uses extension offsets `0x4ef0`, `0x4ef8`, and `0x4f00` (`0x4ea0 + lane*0x50`); the diagnostic rejects nonzero values rather than clearing them.

With those checks passing, the option records one baseline `Tnim_IsLocked` result, invokes the archive's exact lower-level `Tnim_AcquireFrequency(control, 557142UL, 6)` symbol once, logs the stream-gate byte afterward, then calls `Tnim_IsLocked(control)` at 100 ms intervals for up to five seconds. On first RF lock it continues polling for five more seconds so the parent can observe USB bulk activity during a hold period. `TunerLib.o` shows `Tnim_AcquireFrequency` derives the local lane from `control+0x1d30`, builds the per-lane parameter pointer from extension `+0x4e98 + lane*0x50`, and dispatches to `TC_SetFrequency`; `Tnim_IsLocked` dispatches to `TC_IsLocked`, whose terrestrial branch reads register `0xb0` and checks low nibble 9. This is explicitly a lower-level RF diagnostic, not a validated public receive sequence, and a successful RF lock would not itself prove TS output.

`Tnim_AcquireFrequency` also has an internal conditional update of control state at `control+0x90d78` when `control+0x1c70` is zero, based on cached extension bytes; the harness logs only whether that control-state word is nonzero and does not print those bytes. It does not call seed generation, alter `+0x30d60`, modify the tune scratch words, call `StreamDataRead`, or process TS data. The direct vendor primitive is therefore not side-effect-free. This diagnostic calls the lower-level RF component separately; it does not clear or satisfy the public receive-chain readiness gate.

Strict host compile passed with `g++ -std=c++11 -Wall -Wextra -Wpedantic -Werror -fno-stack-protector` and the SDK include directory. `nm -u` confirms references to `_Z21Tnim_AcquireFrequencyP13_STnimControlmh` and `_Z13Tnim_IsLockedP13_STnimControl`. The static-analysis phase did not execute vendor code or access hardware. The parent subsequently linked and ran the bounded trial below.
