# 0.1.0 の実機検証手順

px4-userland v0.1.10 の配布物と、その `docs/release-validation.md` に合わせる。配布するバイナリの種類、ランナーでの生成、短時間確認の順は px4 と同じである。違うのは、バイナリアーカイブへ Linux ローダを同梱することだけである。対応ソースのアーカイブには入れない。Windows は px4 v0.1.10 に無いので、0.1.0 にも無い。

この文書は手順である。ここに書いた項目を、実施済みの検証結果として読まない。

## 今回の 0.1.0 で決まった範囲

2026-10-09 の決定:

- 回帰試験は、下の短時間項目を 8 アーカイブすべてで行う。
- 2 時間ソークも 8 環境すべてで行う。px4 のようにソークの有無や時間をその場で選ばない。
- LNB のテスター測定も、今回に限り 8 アーカイブすべてで行う。以降のリリースでは、LNB の制御を変えない限り測定を省いてよい。
- 製品コード（ドキュメント以外）を変えないこと。変えた場合、その前にランナーが作った候補はリリースに使えない。ドキュメントだけの変更なら、検証結果をコミットしたうえで、その同じランナー成果物をリリースできる。

リリース候補は、px4 と同じく GitHub-hosted runner がまとめた一式である。中身はバイナリ 8 本、対応ソース 1 本、`SHA256SUMS`。HAOS 上で作ったアーカイブは候補にしない。バイナリ 8 本は `firmware/asicen-loader.bin` を同梱する。過去の動的ビルドで PX-W3U3 の T27 と BS01_0 を受信した記録は、この候補の合格にしない。

## アーカイブと環境

各行は別々に実施する。同じアーキテクチャの別アーカイブや、別 OS の結果で代用しない。Linux musl aarch64 は aarch64 の実機上で動かし、CPU エミュレーションを使わない。

| アーカイブ | 環境 | px4 での対応 |
|---|---|---|
| `asicen-userland-0.1.0-linux-glibc-x86_64` | AnduinOS x86_64 | E03 |
| `asicen-userland-0.1.0-linux-musl-x86_64` | HAOS の Alpine/musl | E02 |
| `asicen-userland-0.1.0-linux-glibc-aarch64` | aarch64 の glibc 実機 | E15 |
| `asicen-userland-0.1.0-linux-musl-aarch64` | aarch64 実機上の musl。エミュレーションなし | E15 上の musl |
| `asicen-userland-0.1.0-darwin-arm64` | macOS arm64 | E04 |
| `asicen-userland-0.1.0-android-aarch64` | Termux aarch64 | E05 |
| `asicen-userland-0.1.0-android-armv7a` | Termux armv7a | E06 |
| `asicen-userland-0.1.0-android-x86_64` | Termux x86_64 | E07 |

実施するホスト名、OS の版、`uname -m` は各行の記録に書く。上の環境が用意できない行は未完了であり、他の行の成功で埋めない。Windows、FreeBSD、Android APK は 0.1.0 の対象外。

物理操作は利用者が行う。依頼してから 5 分待ち、超えればその操作を未完了として、そのアーカイブの実機工程を止める。依頼の直前に、この環境では `vibe` を一度だけ鳴らす。

## 各アーカイブの順序

1. 候補の SHA-256 を確認して展開する。使う実行ファイルがそのアーカイブのものであることを記録する。
2. LNB のテスター測定（今回の 0.1.0 だけ、8 本すべて）。
3. アンテナを繋ぎ、短時間の回帰。
4. 同じ候補のまま 2 時間ソーク。
5. プロセス、FD、ソケットの残留を見てから次の環境へ移る。

一台のチューナーを環境間で移す。8 環境のソークだけで 16 時間になる。

### LNB の測定

集合住宅の壁端子や、ほかの給電機に同軸を繋いだまま測らない。測るのはこの箱のアンテナ端子だけとする。給電を要求するときは、W3U2 / W3U3 / V2 の公式説明どおり AC アダプタを付ける。

記録するのは、機種、USB ID、アーカイブ名、SHA-256、要求した電圧、テスターの読み、close または shutdown のあとの読み。

- W3U2 / W3U3: `--lnb-voltage 0` と `15` をそれぞれ測る。ソフトは GPIO20 を active-low で駆動する。15 のあと close または shutdown し、オフ側へ戻ったかを測る。
- W3U3 V2: 同じ要求を測る。ソフトは GPIO20 を active-high で駆動する。保護で給電が切れた場合は、そのときの読みと、オンへ戻らなかったことを残す。
- S3U / S3U2: `15` は `UNSUPPORTED` になることを確認する。ソフトは給電を切り換えない。端子電圧は測って残すが、0V だったとは書かない。

USB 転送の成功や GPIO の読み戻しを、端子電圧の合格にしない。

### 短時間の回帰

`asicend --list` によるハードウェア列挙は未実装なので、発見は `asicen-probe list` を使う。アドレスは挿し直すと変わる。

1. 候補の `asicend --hardware` で起動する。USB 機能が 2 つの W3U2 / W3U3 / V2 は primary と sibling を指定する。USB 機能が 1 つの S3U / S3U2 は primary だけを指定する。
2. 地デジを有限長で受信する。4 チューナー機の露出は primary の receiver 1。S3U は receiver 0 の地デジ側。S3U2 は receiver 1。
3. 衛星を `--lnb-voltage 0` で有限長受信する。4 チューナー機と S3U2 は receiver 0。S3U は receiver 0 を地デジと排他で使う。
4. 同時ストリームは 1 本のままにする。sibling 側の受信や 4 本同時は、この手順の合格条件にしない。
5. 内蔵カードがある個体では、デーモンを起動したままカードを抜き、不在を確認してから戻し、ATR または APDU が戻るかを見る。カードスロットが無い個体は対象外と書く。
6. 受信中に USB を抜き、クライアントが止まって残らないことを見る。挿し直したあとは、古いデーモンの自動復帰を合格にしない。同じ候補から起動し直す。
7. TS は sync、TEI、continuity をオフラインで数えて残す。デーモンの品質カウンタが 0 であることは無誤りの証拠にしない。

コマンド、終了コード、パケット数、カウンタ、ログの置き場を各行に残す。失敗した試行は消さず、やり直した回を別の試行として残す。

### 2 時間ソーク

各環境で、短時間回帰に使った同じ候補のまま 2 時間受信する。同時は 1 本。途中で status、受信の止めと再開、可能ならカードの APDU を挟む。開始時、約 30 分ごと、終了時に FD 数と RSS を残す。数値の固定しきい値は置かない。終わりまで増え続ける場合は判定を保留し、そのアーカイブを公開可能にしない。

## 結果とリリース

結果は日付つきでこのリポジトリのドキュメントに追記する。製品コードは変えない。

8 行の短時間回帰、8 環境の 2 時間ソーク、8 アーカイブの LNB 測定が揃い、ソークの FD 数と RSS が保留条件に入っていないとき、検証結果のドキュメントをコミットし、`4f37ccf` のバイナリをリリースできる。未完了の行がある状態では、対応表だけを更新してリリース済みにしない。

以降のリリースでは、この候補で測った LNB の結果を、LNB 制御を変えていない範囲について省略できる。受信・カード・USB の短時間回帰は、px4 と同様に配布アーカイブごとに残す。ソークの時間と対象は、そのリリースで改めて決める。
